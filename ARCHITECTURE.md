# Architecture

Switchyard is moving from a prototype (an Electron app with a Node server) to one Go binary,
`sy`, that is both the client on every machine and the hub. The plan is
[docs/plan.md](docs/plan.md); the contract is [docs/spec/](docs/spec/); the work is split into
phases in [docs/phases/](docs/phases/). Unofficial; not affiliated with Anthropic.

## Data flow

```
 Claude Code (each session, each config folder)
   │ hook stdin JSON              │ status-line stdin JSON        transcripts, claude agents
   ▼                              ▼                               ▼
 sy hook                       sy statusline                   sy scan / sy agents (timer)
   └──────────────┬───────────────┴───────────────┬───────────────┘
                  ▼  one record per fact (record.md)
          outbox: <state>/outbox/YYYY-MM-DD.jsonl  (outbox.md; fsynced, locked append)
                  │
                  ▼  sy flush (after each hook, debounced; and every minute)
          POST /v1/ingest   bearer machine token (tokens.md)
                  │
   ┌──────────────▼───────────────────────────────── hub (sy hub serve) ─────┐
   │ ingest ─► record table (raw, every field) ─► typed tables (schema.sql)  │
   │                          │                                              │
   │             state engine (states.md)   usage model (windows, pace)      │
   │                          └──────────┬───────────┘                       │
   │                   read API + /v1/stream (SSE)                           │
   │                          │ after each ingest batch: engine.Notify       │
   │      alert engine (push.md): reconcile ─► alert rows ─► scheduler       │
   │                          └─► senders: Web Push (VAPID, RFC 8291), ntfy, │
   │                              link (Android app; widget refresher)      │
   └──────────────────────────────────────┬───────────────────┬──────────────┘
                                          ▼                   ▼ outbound HTTPS
               web board / phone app (webui/, PWA),     push services (FCM, Apple,
               store app (phone/), desktop app,          Mozilla), ntfy servers
               terminal pane
```

Phase 4 adds the phone: the board is an installable web app (pwa.md) paired by a one-time
code or QR (pairing.md), and the hub's alert engine sends pushes when a session needs you
(push.md). The phone app needs the hub on `https://` (`tailscale serve --bg 8787`); pushes
themselves leave the hub over outbound HTTPS and need no inbound route.

Phase 8 adds a store app (`phone/`, phone.md): an Expo app paired like the PWA (it claims
with `cookie: false` and keeps its token in the OS keychain), with the same screens read by
polling the hub API. On Android its notifications arrive over the app's own connection to the
hub (the `link` channel, push.md 13), with no push service; Snooze and Seen buttons call the
same `/v1/actions/{token}`. Widgets and the Live Activity show a snapshot the app writes after
each refresh; the hub keeps the Android widgets fresh with `refresh` frames over the link.

```
 hub ── link sender ─► link queue ─► app's own connection (phone/, Android)
  ▲                                                                       │
  └──────────── read API (polling), /v1/actions/{token} (Snooze, Seen) ◄──┘
                                         app ─► widget snapshot ─► widgets, Live Activity
```

Phase 5 adds remote machines (machines.md). `sy machine add` installs and connects `sy` on
a server over the operator's own `ssh`, in one of three reaches: **direct** (the server posts
to the hub, as above), **forward** (it posts to a loopback port that an SSH connection from
the laptop forwards to the hub; `hub.dial`), or **pull** (the hub runs
`ssh <server> sy outbox drain --stdio` on a schedule and feeds the records to the same
ingester). A server can also send ntfy itself when the hub has not heard from it (direct
push), from a policy it fetches from the hub. `sy update` replaces the binary (also across
the fleet), and `sy hub export` / `import` move the hub, freezing the old one.

```
 server (reach pull)                                 hub (sy hub serve)
   outbox ─► sy outbox drain --stdio ◄── ssh ─── pull scheduler ─► ingest (same as /v1/ingest)
               (drainproto: hello, batch, ack, refuse)
```

The desktop app (phase 6, `app/`) adds `web_usage` records: each account tab's claude.ai
usage is read in the Electron main process and handed to `sy outbox append` (stdin, argv
from an allow-list), then `sy flush` sends it as above. The app reads the hub back through a
desktop token (`sy desktop token`), shows the board in its Hub view, and turns hub alerts into
OS notifications.

```
 app/ (Electron main) ── usage read per tab ─► sy outbox append ─► outbox ─► sy flush ─► POST /v1/ingest
        ▲                                                                              │
        └──── GET /v1/accounts, /v1/stream (desktop token) ◄─────────────── hub ◄──────┘
```

Phase 7 adds the terminal (terminal.md): `sy board` is a live board in any terminal, with no
desktop app. It only reads: from the hub (`/v1/stream` plus the read API, merged with the
local outbox when the hub is away) or, with no hub, from the local outbox. The Claude Code
pane mod and Warp reach the same view through `sy`.

```
 terminal pane
   sy board --follow  ◄── /v1/stream (hub; read API for the first frame)  or  the local outbox
        ▲   (internal/board, board/hubsrc; rendered by board/tui, or as NDJSON frames)
        │ spawns `sy board --follow --ndjson`
   plugin/switchyard-pane (Claude Code mod) ── Enter on a row ──► sy term focus <session>
                                                                    └─► OS opener (allow-listed URL)
```

Keys, the link and peers (keys.md, link.md, peers.md) add a second, separate path next to
ingest. Each device holds Ed25519/X25519 keys; the hub's key and your owner key (sealed on your
own machine, `sy keys`) are pinned on every device, and a device certificate needs both
signatures. Devices keep one signed `/v1/link` connection to the hub (WebSocket, long-poll
fallback) with a durable per-device queue; the hub sends signed `matrix` and `peers` frames and
queued, sealed `peer_msg` frames over it, and the Android app receives its alerts the same way
(`sy-link`, push.md 13-14). `sy agent` is the per-machine service that holds the link, a
session directory and the control socket `sy peers` talks to, and is the only process that
writes into another session's inbox. The hub relays sealed peer messages and keeps only
metadata (`peer_message`, `peer_audit`); it never sees text.

```
 session A ── sy peers send ─► agent.sock ─► sy agent (A's machine) ──┐ same machine: inbox of B
                                                 │ seal to B's machine, sign        │
                                                 ▼                                  │
                                    hub: /v1/link, matrix check, queue ──► sy agent (B's machine) ─► inbox of B
 phone (sy-link) ◄── sealed alert frames over its own /v1/link ◄─ hub alert engine (link channel)
```

Nothing on the hub can make a client do anything: replies are lists of accepted ids.

In phase 1 there is no hub: `sy status` folds the outbox locally with the same state code.

Rules:

- `cmd/sy` only routes to packages; no logic there.
- Client packages never import `internal/hub/...`, with one exception: the pure state fold
  in `hub/state`, so `sy status` and the hub can never disagree. That fold imports only
  `record`.
- `internal/hub/push/...` never imports `hub/api`, `hub/cli`, `hub/pair` or `webui`: the API
  calls the engine (`api.Engine`, `model.AlertService`), never the other way round, and
  alerts reach the stream through the `events.Broker` the engine is handed. `push/model` and
  `push/clock` are leaves, `push/rules` imports only `push/model`. Enforced by
  `internal/hub/push/deps_test.go` (`go list -deps`).
- `internal/drainproto` is a leaf that both the client (`sy outbox drain`) and `hub/pull`
  import. `internal/directpush` imports only the pure `hub/state` fold from the hub side.
  `hub/pull` hands records to the ingester (`ingest.IngestWith`, `Contact`), never to the
  HTTP API; it imports `hub/api` only for the `Puller` interface types the API calls it
  through. Enforced by `internal/hub/pull/deps_test.go`.
- Test seams that must not reach a release build use the `fakeclock` build tag
  (`internal/hub/cli/hooks_fakeclock.go`: fake clock control socket, test push client); the
  end-to-end test in `test/e2e/push` builds `sy` with it.
- The `fakeopen` build tag (`internal/termctl/fakeopen.go`) is the same kind of seam: with
  `SY_TEST_OPENER=<file>` the OS opener records its argv instead of running; the terminal
  end-to-end test in `test/e2e/terminal` builds `sy` with it. Release builds contain neither
  `fakeclock` nor `fakeopen`; `scripts/ci/check-release-seams.sh` (`make release-check`, a CI
  step) builds with and without the tags and fails if the release binary has either seam.
- `internal/board/**` never imports hub internals beyond the pure `hub/state` fold (and
  `status`, which itself imports only that fold): no `hub/store`, `hub/api`, `hub/ingest` or
  `hub/cli`. It never calls `/v1/ingest` and never imports `internal/client` or
  `hub/ingest`; the board only reads. Enforced by `internal/board/noingest_test.go`.
- `internal/board/tui` depends only on `board` (and `termenv`); `board/hubsrc` only on `board`
  and `atomicfile`. `internal/termenv` is a leaf. `internal/termctl` and `internal/warp` see
  the machine only through a `termenv.Env`.
- `board`, `termctl`, `warp` and `termenv` never call `os.UserHomeDir` or read `HOME`
  (or `USERPROFILE`) themselves: the caller injects the environment, so tests run against
  temp homes and a real config is unreachable. Enforced by `internal/termenv/lint_test.go`.
- Hub packages talk to each other only through the store or plain function calls on
  records; no package reaches into another's tables (plan section 7: "Each part talks to the
  others only through the store").
- Dependencies stay minimal: standard library first; `modernc.org/sqlite` (pure Go, so builds
  stay `CGO_ENABLED=0` static binaries); a TOML parser in phase 1. Each new dependency is
  justified in the phase file that adds it.

## Building

```
make build        # ./dist/sy
make check        # gofmt, go vet, go test ./..., spec checks
make e2e-terminal # sy board / term / open / ssh end to end (fake opener, temp HOME)
make pane-check   # the Claude Code pane mod gate (needs claude on PATH)
make release-check  # a release build has no fakeclock or fakeopen seam
```

The prototype still uses `npm start` / `npm test` (see README.md). The new desktop app has
its own targets, which only run npm inside `app/`:

```
make app-test     # lint + unit tests (no display, no Electron binary)
make app-smoke    # Electron smoke S1-S12 under xvfb, against a real hub built from here
make app-dist     # bundled sy + packages in app/dist (never signed, never published)
make app-e2e      # the packaged AppImage end to end (after app-dist)
```
