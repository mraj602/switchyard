# Contributing to Switchyard

Thank you for helping. This page covers the development setup for each component, the checks a
change must pass, how behaviour changes are specified, and how pull requests are reviewed.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report security
problems privately, as [SECURITY.md](SECURITY.md) explains, not in an issue.

## Ways to help

- Report a bug or a confusing step in the docs (use the issue templates).
- Try Switchyard on a setup we have not tested: another Linux distribution, macOS on Intel,
  Windows, an unusual terminal, an Android phone maker with strict battery rules.
- Pick an issue labelled `good first issue` or `help wanted`.
- Improve a guide in [docs/guide/](docs/guide/README.md).

For anything larger than a small fix, open an issue or a discussion first so we can agree on
the behaviour before you write code.

## Development setup

### `sy`, the hub and the board

Needs Go 1.27 or newer, `make`, and Python 3 with `pyyaml` for the spec checks
(`pip install -r scripts/ci/requirements.txt` adds the OpenAPI validator too). The `sqlite3`
CLI is optional.

```sh
make build        # ./dist/sy
make check        # gofmt check, go vet, go test ./..., spec checks
```

Run a throwaway hub without touching your real setup by pointing `sy` at a temporary home:

```sh
export SY_HOME="$(mktemp -d)"
./dist/sy hub serve --listen 127.0.0.1:8799
```

For board work, `go run ./cmd/webui-dev -dir webui/static` serves the board files from disk
against a mock hub, so you can edit them and reload. Sign in with the token it prints, or start
it with `-noauth`.

### Desktop app

Needs Node.js 22 or newer and the Go toolchain (the smoke tests build `sy`). npm runs only
inside `app/`.

```sh
make app-test     # lint and unit tests, no display needed
make app-smoke    # Electron smoke tests against a real hub built from this tree
make app-dist     # packages in app/dist, unsigned
make app-e2e      # the packaged AppImage end to end (after app-dist)
```

Smoke and end-to-end tests need a display. On Linux they run under `xvfb-run` when it is
installed. See [app/README.md](app/README.md).

### Android app

Needs Node.js 22.13 or newer. Building an APK also needs JDK 17 and the Android SDK
(`ANDROID_HOME`). npm runs only inside `phone/`.

```sh
make phone-check            # typecheck, lint, unit tests, secret check, prebuild checks
make phone-android-debug    # an unsigned debug APK for your own phone
make e2e-android            # on an emulator against a real hub (needs an AVD and KVM)
```

`phone/android` and `phone/ios` are generated by `expo prebuild` and never committed. See
[phone/README.md](phone/README.md).

### Claude Code plugin and pane mod

```sh
make pane-check   # needs claude on PATH
```

## Checks a change must pass

Run the checks for every component you touched before opening a pull request. CI runs the
same ones.

| You changed | Run |
| --- | --- |
| Go code, `docs/spec/schema.sql`, `docs/spec/api.yaml` | `make check` |
| `internal/board`, `internal/termctl`, `internal/warp`, terminal commands | `make check` and `make e2e-terminal` |
| `internal/setup`, `install/` | `make check` and `make e2e-setup` (needs podman or docker) |
| `internal/machines`, `internal/sshx`, outbox drain | `make check` and `make e2e-machines` (needs podman or docker) |
| `webui/` | `make check` (the hub serves it; there are Go tests for the embed) |
| `app/` | `make app-test`, and `make app-smoke` for anything visible |
| `phone/` | `make phone-check` |
| `plugin/switchyard-pane/` | `make pane-check` |

Tests never use your real home folder, Claude Code config or credentials: every suite runs
against temporary folders, fake `claude` binaries and fixture data. Keep it that way. A test
that needs a real account or a real claude.ai sign-in does not belong in the automated suites;
add it to the manual walk-through in [docs/TESTING.md](docs/TESTING.md) instead.

`testdata/` holds redacted payloads captured from real Claude Code runs.
`scripts/fixtures/regenerate.sh` makes new ones; it runs real Claude sessions, so it is for
maintainers, and `scripts/fixtures/check-redaction.sh` must pass before any fixture is
committed.

## Specs first

The specs in [docs/spec/](docs/spec/README.md) are the source of truth for behaviour: records,
the API, the database schema, session states, setup, alerts, keys, peers and the apps.

- A change in behaviour updates the spec in the same pull request, before or with the code.
- If the code and the spec disagree, the spec is right until a pull request changes it.
- A new dependency needs a reason in the pull request. Go code prefers the standard library;
  builds stay `CGO_ENABLED=0`.
- Bug fixes that restore spec behaviour need no spec change.

## Style

- Go: `gofmt`, `go vet`, small packages with one job, and the dependency rules in
  [ARCHITECTURE.md](ARCHITECTURE.md#go-packages). Errors and user-facing text are plain
  sentences.
- JavaScript and TypeScript: the ESLint configs in `app/` and `phone/`.
- User-facing text and docs: plain, direct English; say what happens and what to do next. Use
  the names Switchyard, hub, board, desktop app, Android app and `sy`. Never use Anthropic's
  logos, and refer to Claude and Claude Code only to describe compatibility.
- Never log or store credentials, cookies, prompts or code. See
  [docs/guide/security.md](docs/guide/security.md) for what records may hold.

## Commits

- One logical change per commit, with a short summary line in the imperative ("Add ntfy
  retry", "Fix reset time on idle accounts"), and a body that says why when it is not obvious.
- Sign off every commit under the [Developer Certificate of Origin](https://developercertificate.org/)
  (below).

### Developer Certificate of Origin

Switchyard does not ask for a contributor licence agreement. Instead, every commit carries a
`Signed-off-by` line, which certifies that you wrote the change or have the right to submit it
under the project's licence (Apache-2.0), as set out in the DCO 1.1 text at
<https://developercertificate.org/>.

Add it with `-s`:

```sh
git commit -s -m "Fix reset time on idle accounts"
```

which appends:

```
Signed-off-by: Your Name <you@example.com>
```

Use your real name or a consistent pseudonym, and an email address you control. To sign off
commits you already made: `git rebase --signoff main`.

## Pull requests

1. Fork the repository and create a branch from `main`.
2. Make the change, with tests and the spec update if behaviour changes.
3. Run the checks for the components you touched.
4. Open a pull request against `main` and fill in the template.
5. A maintainer reviews it. Expect questions about behaviour, privacy and failure cases.
   Please keep the conversation in the pull request.
6. Once CI is green and the review is approved, a maintainer merges it, usually as a squash
   merge.

Changes to the following get extra review and may take longer: anything that reads or sends
data from claude.ai, the content rules for records, tokens, pairing, keys and signatures, the
desktop app's security settings, and the install and update paths.

## Good first issues

Issues labelled `good first issue` are small and well specified. Typical ones:

- A clearer error message or `sy doctor` hint.
- A missing test for an existing spec rule.
- A docs fix, or a guide step that did not match what you saw.
- Board accessibility: labels, focus order, contrast.

Comment on the issue before you start so two people do not do the same work.

## Releases

Maintainers cut releases from `main` with a `v<version>` tag. Release builds are made by CI,
with checksums and build attestations. The Android APK is signed by a maintainer with the
project key outside CI. Contributors do not need to do anything for a release.
