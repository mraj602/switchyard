# Phase 3: Installer and sharing

From plan section 16. Branch `phase-3`, tag `v0.3`. Needs phase 2 for the hub step
(`sy hub serve`, `sy hub token create`); everything else needs only phase 1. The behaviour
is fixed in [docs/spec/setup.md](../spec/setup.md); this file says who builds what, in which
files, and how it is proven.

## How the work is split

Three waves. Wave 1 is four (optionally five) agents in parallel, each owning disjoint
files. Nobody edits a file owned by another package; a needed change goes back to the
owner as a request. `cmd/sy/main.go`, `go.mod` and `go.sum` are touched only in wave 2
(new dependencies are listed by each package and added at merge with `go mod tidy`).

```
wave 0  contract (1 agent, ~0.5 day)        internal/setup/model, internal/claudecli (interface + fake),
                                            plugin/embed.go
wave 1  parallel (4–5 agents, ~3 days)      A planner+detect · B apply+backup+undo · C share+jsonedit
                                            · D accounts+plugin+service+fake claude · E release+install+skill
wave 2  integration (1–2 agents, ~2 days)   F cmd wiring, prompts, uninstall, doctor, tick · G end-to-end
```

### What CI cannot cover, and how it is handled

- **macOS Keychain and real logins**: not testable in CI (no Claude login there). The fake
  makes logins file-based. Before tagging, one manual run on a real Mac: S1 with the real
  `claude`, logging in one folder; noted here with the date.
- **Real Claude Code behaviour drift**: the fake contract test (WP-D) against the real
  `claude`, run by hand on the laptop before tagging and after each Claude Code update.
- **Hooks actually firing from the `sy-local` plugin and the settings-env plugin root**:
  the phase 1 E2E test (`SY_E2E_CLAUDE=1`) is extended to a throwaway HOME set up by
  `sy setup`, with a real `claude -p` in a second folder that gets its plugin root only from
  settings `env` (risk 2 of setup.md).
