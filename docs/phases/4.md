# Phase 4: Phone web app and pushes

From plan section 16. Branch `phase-4`, tag `v0.4`. Needs phase 2 (hub, board, stream). It
touches phase 3 only at `sy setup` step 5 and `--code` (wave 2). The behaviour is fixed in
[pairing.md](../spec/pairing.md), [push.md](../spec/push.md), [pwa.md](../spec/pwa.md) and
`api.yaml` (phase 4 operations, all marked `x-reserved: phase 4` until built). This file says
who builds what, in which files, and how it is proven.

## Key decisions (details in the specs)

| # | Decision | Where |
| --- | --- | --- |
| 1 | One SPA: the phase 2 board becomes the installable app (manifest, service worker, More/Alerts/Settings/Pair). No separate phone codebase. | pwa.md 1 |
| 2 | Pairing code = 6 digits (typed) + 128-bit secret (QR). QR is an `https://<hub>/#/pair?s=…&c=…` URL, so the phone camera opens it; the fragment never reaches the server. No hub public key in the QR (HTTPS authenticates the hub). | pairing.md 2.2 |
| 3 | Typed codes are rate limited per IP and hub-wide; QR secrets are exempt from the hub-wide lockout, so a lockout cannot block pairing. | pairing.md 3.3 |
| 4 | iPhone: Safari does not claim; the installed Home Screen app claims with the typed code (separate cookie jar). Android claims at once. | pairing.md 5 |
| 5 | The phone's token lives only in the `HttpOnly` `sy_session` cookie (400 days, refreshed daily); state-changing cookie requests need JSON content type and a matching `Origin`. | pairing.md 3.2 |
| 6 | Owner scope (pairing, devices, global rules) comes from a one-time `sy hub owner-link` → 30-day owner session. Password/passkey deferred to phase 6. | pairing.md 4 |
| 7 | Global rules decide if and when an alert fires; per-device prefs (mute, own quiet hours, private, tap) decide which devices hear it. Phones edit only their prefs. | push.md 1, 5.4 |
| 8 | Alerts follow state by **reconcile** (compare wanted episode with stored alerts) after each ingest batch and at start; one alert per episode via a unique key. Timers are columns, so restarts resume. | push.md 3.2, 3.5, 3.6 |
| 9 | Due = `clamp(since + delay, now, now + delay)`; stale guard 15 min; `awake_at` guard against hub downtime and laptop suspend; first-start baseline sends nothing. | push.md 3.3, 3.8 |
| 10 | Web Push implemented in-house on the standard library (`crypto/ecdh`, `crypto/hkdf`, GCM, ES256), ~250 lines, tested against RFC 8291's example; `webpush-go` rejected (one release since 2023, adds two deps). | push.md 6.1 |
| 11 | ntfy: random 143-bit topic, JSON publish, Open/Snooze/Seen actions; Snooze/Seen call `/v1/actions/<signed token>` (HMAC, 24 h, applies once per fire). Private forced on for ntfy.sh. | push.md 7, 8 |
| 12 | Web Push payloads are end-to-end encrypted, so private mode there only protects the lock screen; it matters most for ntfy. | push.md 5.5 |
| 13 | Schema v3 drops and recreates the never-written v1 placeholder tables (`pair_code`, `channel`, `push_target`, `rule`, `alert`, `delivery`), adds `hub_secret`, `device.expires_at`, `device.prefs`. | push.md 9 |
| 14 | QR library `rsc.io/qr` (pure Go, no deps). The only new dependency of the phase. | pairing.md 2.2 |
| 15 | Analytics under More is deferred (its API has been reserved since phase 2). | pwa.md 3 |

## How the work is split

```
wave 0  contract (1 agent, ~0.5 day)     migration v3, route table, shared types, clock, wiring stubs
wave 1  parallel (4 agents, ~3 days)     A pairing+devices+CLI · B rules engine+scheduler+alerts API
                                         · C channels (webpush, ntfy)+targets API · D PWA/webui
wave 2  integration (1 agent, ~1.5 days) serve wiring, setup step 5, docs, end-to-end, device checklist
```

Nobody edits a file owned by another work package; a needed change goes to the owner as a
request. `go.mod`/`go.sum` change only in wave 0 (`rsc.io/qr`). Each WP deletes the
`x-reserved: phase 4` line of **its own** operations in `api.yaml` and flips them to
implemented in its handler file, nothing else in that file.

## Open risks

1. **iOS web push quirks.** Apple's VAPID `sub` validation (`BadJwtToken`), notification
   delivery while Focus modes are on, and no action buttons on iOS. Mitigation: `vapid_subject`
   is configurable; Snooze/Seen exist in the app; ntfy as fallback.
2. **iOS pairing friction.** The installed app must be paired by typing the code (separate
   cookie jar). If iOS turns out to copy Safari's cookies at install, the flow could be
   simplified; untested either way.
3. **Reachability.** Opening the app, tapping a push and ntfy's Snooze/Seen need the tailnet;
   pushes themselves do not. Away from Tailscale, only the Remote Control link works, and
   whether iOS opens it in the Claude app (and in the right account, plan section 12) is
   unverified.
4. **Remote Control link freshness.** A stored `remote_url` does not prove Remote Control is
   still on; `skip_remote` may then suppress pushes Claude's app will not send. Off by default.
5. **Timing of cancel-if-answered** depends on `sy flush` reaching the hub within the delay.
   With the hub merged on a sleeping laptop or behind an SSH forward, an answer can arrive
   after the push; the 40-second test assumes a reachable hub.
6. **Stale guard trade-off.** After a long outage the hub sends nothing for episodes older than
   15 minutes; the board still shows them. Silence alerts depend on `awake_at`, which needs
   the jump detection to work on macOS and Linux suspend (tested with the fake clock only).
7. **Headless push testing is partial.** Real subscription and delivery through Google/Apple
   cannot run in CI; the fake push service and CDP-delivered pushes cover our code, the device
   checklist covers the rest.
8. **Own crypto.** Web Push encryption is implemented in-house; the RFC vector and an
   independent decoder reduce the risk, and a mistake shows up as pushes that never display
   (fails loudly in the test push), not as a leak.
9. **ntfy.sh topics are public by name.** Private mode is forced on for ntfy.sh and action URLs
   expose only the hub host name, but a leaked topic lets someone read pushes and spam the
   phone. Self-hosted ntfy with a token is recommended for full text.
10. **Owner sign-in only from the hub's shell.** Until phase 6 adds a password or passkey, the
    owner must run `sy hub owner-link` on the hub (`docker compose exec …`) to pair from the
    board or change rules.
11. **CI between wave 0 and the spec edit.** `api.yaml` already carries the phase 4 operations,
    so `TestEveryAPIPathIsRouted` fails on `main` until wave 0's first task lands; do it first.
12. **Phase 3 overlap.** `sy setup` step 5 and `--code` live in phase 3's files; wave 2 must
    coordinate if phase 3 is still in progress.
