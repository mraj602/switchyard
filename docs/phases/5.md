# Phase 5: More machines

From plan section 16. Branch `phase-5`, tag `v0.5`. Needs phase 2 (hub, ingest, board) and
phase 3 (`sy setup`, release archives, `install.sh`); uses phase 4's pairing codes, alert
engine and ntfy format. The behaviour is fixed in [machines.md](../spec/machines.md), with
changes to [record.md](../spec/record.md) (3.1 dedupe, 4.8 `machine_info`, 4.9 `direct_push`),
[outbox.md](../spec/outbox.md) 8, [push.md](../spec/push.md) 3.1–3.3 and 3.6,
[tokens.md](../spec/tokens.md) 3–4, [setup.md](../spec/setup.md) 4, [paths.md](../spec/paths.md)
and [pairing.md](../spec/pairing.md) 2.4. This file says who builds what, in which files, and
how it is proven.

## Key decisions (details in the specs)

| # | Decision | Where |
| --- | --- | --- |
| 1 | `sy machine add` runs on the operator (laptop) with the person's own SSH; the remote never needs internet for the install: the operator fetches the release for the remote's `os/arch`, verifies it against `SHA256SUMS`, streams it, and compares the SHA-256 on the remote before the atomic `mv`. | machines.md 4.2 |
| 2 | Joining uses a machine pairing code minted through an **admin channel** (`local`, or a command prefix such as `ssh oci sy` / `… docker compose exec -T hub sy`, or a pasted board code). The remote gets the 128-bit **secret** on stdin (`--code-stdin`), never as an argument and never the typed digits. | machines.md 4.4, 10.2 |
| 3 | Logins on the remote are a separate `ssh -t … sy account login <folder>` per folder with the person's terminal inherited; the code passes through the PTY to Claude Code; `sy` never sees it. | machines.md 4.2 step 8 |
| 4 | Three reach modes stored as `hub.reach`: `direct`, `forward`, `pull`. `auto` picks `direct` only when the remote's own `/health` probe works, else asks; never guesses under `--yes`. | machines.md 3.1 |
| 5 | Forward mode: a marked block in `~/.ssh/switchyard.conf` (+ one `Include` first in `~/.ssh/config`), a **fixed per-machine port** (47830…47849), and a new `hub.dial` key so TLS stays end to end (URL names the hub, dial goes to the forward). Unix-socket forward is an option, not the default (sshd's `StreamLocalBindUnlink`). | machines.md 3.3 |
| 6 | Pull mode needs **no relay scope**: the hub runs `ssh` itself and ingests in-process as a **pull device** whose token is discarded. The remote has no token; the hub's key is limited by `restrict,command="…/sy outbox drain --stdio"`. | machines.md 3.4, tokens.md 3 |
| 7 | Drain protocol: line-delimited JSON frames over the SSH channel, **stop-and-wait** batches, the ack is the ingest reply plus `seq`, applied with the same function as `sy flush`. Hub commits before acking; the cursor moves only on a matching ack, so nothing is lost or stored twice. Replaces outbox.md's reserved `--ack <file:offset>`. | machines.md 3.5 |
| 8 | Pull host keys are **pinned at registration** from the operator's already-verified SSH session (the probe prints the remote's `ssh_host_*_key.pub`), stored in the hub database, and checked with `HostKeyAlias` + `StrictHostKeyChecking yes`; `sy` never disables host key checking anywhere. | machines.md 3.4, 10.1 |
| 9 | Dedupe: a record id already stored from another device **of the same machine** is a duplicate, not `id_conflict` (reach changes, re-pairing, hub moves). | record.md 3.1 |
| 10 | Direct ntfy covers only the three session triggers (the machine folds its own outbox with the shared state fold, so its episode key equals the hub's). It fires only when the hub has not answered the entering record **and** has not been reached for `after_s`. The hub learns through a new `direct_push` record kind; a **catch-up hold** on overdue alerts from a machine with backlog avoids a double push. | machines.md 5, push.md 3.2–3.3 |
| 11 | The direct-push policy is the hub's rules resolved per machine (`GET /v1/push/direct-policy`, write scope, seats as account/org pairs, first match wins), so the machine picks the rule the hub would. | machines.md 5.3 |
| 12 | Machines learn the hub's `record_v_max` from `/health`, every ingest reply and the drain `start`; **a client never sends a record above it** and holds it at the cursor (reported as `held`). The hub reads every older `v` forever. All `v` stay 1 in phase 5; this is the mechanism for later phases. | machines.md 7.2 |
| 13 | New record kind `machine_info` carries os/arch/version/reach/outbox health/direct-push state; it fills the Machines screen and is replayable like every other fact. | record.md 4.8 |
| 14 | `sy update` is install.sh in Go (`internal/update`): no GitHub API, SHA-256 against `SHA256SUMS`, optional `gh attestation verify`, smoke-run before replace, `sy.old` for `--rollback`, refuses package-manager installs and schema-incompatible hub downgrades. `--machines` updates the hub host first, then the rest to the operator's version, pushing the archive over SSH when a remote has no internet. The hub never starts an update. | machines.md 7.3, 7.4 |
| 15 | `sy hub export` **freezes** the hub (ingest re-checks the flag inside its write transaction; pull and pushes pause), snapshots with `VACUUM INTO`, and packs the pepper and the pull key; optional passphrase encryption with PBKDF2 + AES-GCM from the standard library. `import` refuses any non-empty hub, has no `--force`. Machines keep their tokens and run `sy connect <new> --keep-token`; nothing follows `moved_to` automatically. | machines.md 8 |
| 16 | Schema v4: `machine` gains reach, record_v, held, backlog age, info; new `pull_target`. | machines.md 9 |
| 17 | No new Go dependency: `ssh`/`ssh-keygen`/`ssh-keyscan` are run as programs; crypto is `crypto/pbkdf2`, `crypto/aes`, `crypto/cipher`. | — |
| 18 | E2E over real SSH with **podman** containers running `sshd` (docker in CI, as phase 3), never `StrictHostKeyChecking=no` in tests either: test known_hosts are filled from the containers' host keys. | Test plan |

## How the work is split

```
wave 0  contract (1 agent, ~0.5 day)      api.yaml paths + route table, schema v4, record kinds, drainproto,
                                          config keys, Health/IngestReply/Heartbeat fields, update API stubs,
                                          command stubs
wave 1  parallel (4 agents, ~3–4 days)    A machine add + SSH + setup/connect · B drain + pull + version hold
                                          · C hub machines model + ingest + direct push · D update + export/import
                                          + Machines screen
wave 2  integration (1 agent, ~2 days)    serve/tick/flush wiring, doctor, deploy, ARCHITECTURE, e2e (podman sshd)
```

Nobody edits a file owned by another work package; a needed change goes to the owner as a
request. `go.mod`/`go.sum` do not change in this phase (decision 17). Each WP deletes the
`x-reserved: phase 5` line of **its own** operations in `api.yaml` when it registers the
handler, nothing else in that file.

## Open risks

1. **Forward mode is fragile by nature.** Records flow only while an SSH connection holds the
   forward; a second window cannot take over the port until the first one's connection dies
   (up to ~90 s with `ServerAliveInterval 30`). Recommend `direct` or `pull` whenever possible;
   the screen says "via laptop SSH" so the trade-off is visible.
2. **Local users on a forwarded server** can reach the hub's unauthenticated endpoints through
   `127.0.0.1:<port>`. Rate limits and tokens bound the damage; `--forward-socket` closes it
   but depends on sshd's `StreamLocalBindUnlink` (machines.md 12.1).
3. **Pull from a Docker hub** needs the SSH client in the image, the key in the state volume,
   and network reach from the container to the servers (Tailscale sidecar or host network).
   Documented in deploy; not every setup will have it.
4. **Direct push duplicates** remain possible when the hub stored the entering record but its
   reply was lost, or when a client clock is more than 5 minutes ahead. Bounded by the 15 s
   grace, the catch-up hold and the stale guard; visible in the Alerts log as
   `direct_push duplicate`.
5. **Policy staleness.** A pull-mode machine never fetches the direct-push policy (no token)
   and uses defaults unless a policy file is copied; a rule changed on the hub reaches direct
   pushes only after the next hourly fetch.
6. **`claude auth login` through `ssh -t`** is verified only with the fake claude until the
   manual check; if Claude Code changes its login flow, the fallback is the printed command.
7. **Self-update of a running binary**: Unix rename is safe; Windows relies on renaming a
   running `.exe` and cleaning up later. Package-manager installs are refused rather than
   fought.
8. **Export files are crown jewels** (VAPID private key, ntfy tokens, pull key, pepper, every
   token hash). Mode 0600, a loud warning and optional encryption; nothing stops a person from
   copying it somewhere unsafe.
9. **Frozen old hub forever.** After a move the old hub keeps answering 503 so unmoved machines
   keep their records; if it is simply switched off instead, they still keep them (network
   errors), so this only matters if someone unfreezes it by mistake.
10. **Shell diversity on remotes.** Remote commands are single-quoted plain words and fixed
    `sh -c` scripts; exotic login shells (`nu`, `xonsh`) are not tested and may fail at step 1
    with a clear error.
11. **CI time.** The SSH scenarios need containers and take minutes; M1–M4 and M6 run in CI
    (docker), M5, M7–M9 run nightly and locally with podman, `cut_test.go` runs on every push.
12. **Phase 3 overlap.** WP-A edits `internal/setup/**` and `cmd/sy/setup*.go` (hub flags only);
    if phase 3 work is still open, coordinate with its owner as phase 4 did.
