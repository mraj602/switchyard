# Phase 7: Terminal pane and Warp hookups

From plan section 14 (layers 1 and 2) and section 16. Branch `phase-7`, tag `v0.7`. Needs
phase 2 (hub, read API, `/v1/stream`) and phase 3 (`sy setup`, plugin install, apply, backup
and ledger). It also uses phase 5's journal pattern (`machineadd/forward.go`) and phase 6's
`sy desktop token`. Phase 7 has two parts:

1. **The session board in any terminal.** `sy board` is a dense TUI that runs in a split, a
   tab or tmux. Next to it is the **pane**: a Claude Code mod that draws the same board as a
   side pane, plus a band above the prompt, inside Claude Code itself. The data comes from
   the hub, or from this machine's outbox when there is no hub.
2. **Warp hookups with no fork.** These are `OSC 2` tab titles with the account in them, a
   tab config per account in that account's colour (opened by `sy open <label>`),
   click-to-focus through `WARP_FOCUS_URL` (also across `sy ssh`), and Warp's own Claude
   Code plugin in every account folder.

Warp stays the terminal and has no plugin API. The optional Warp fork (layer 3) is phase 9
and out of scope. This file says who builds what, in which files, and how it is proven.
Wave 0 moved the **Contract** sections (T1–T12) to
[docs/spec/terminal.md](../spec/terminal.md), which is now the source.

Screens: `docs/design/screens/TermPane.dc.html` (the pane, band and status line). Only the
"New Claude tab as" menu of `TermWarp.dc.html` is in scope, as `sy open`; the rest of that
screen is phase 9.

## Hard rules

1. **No live settings or Warp config is touched without an explicit `sy` command.** `sy`
   never changes `~/.claude*/settings.json` (or any settings target behind a link), Warp's
   own settings, or any Warp folder as a side effect. Only these commands change them:
   `sy term setup …`, `sy term titles on|off`, `sy term warp on|off`, `sy term off`,
   `sy setup --terminal …` and `sy uninstall`. Each one goes through the phase 3 machinery:
   - it computes a plan and prints it; `--dry-run` stops there;
   - it holds `setup.lock`;
   - it writes a backup set and journal (setup.md 7) before each change;
   - it updates the ledger (setup.md 9.3);
   - `sy setup --undo [id]` reverses it.

   `sy board`, `sy open`, `sy ssh`, `sy term focus` and the hooks write nothing outside
   `<state>`.
2. **Warp files: ours only.** In Warp's folders, `sy` writes only `switchyard-*.toml` files in
   `tab_configs/`. It never writes Warp's settings file (so not `directory_tab_colors`),
   launch configurations, themes or keybindings. A `switchyard-*.toml` whose hash differs from
   what `sy` wrote now belongs to the person: it is left alone, reported, and never
   overwritten or removed.
3. **Read only, never type.** The board and the pane read state. They never write to another
   session's terminal, never send keystrokes and never approve anything. The pane mod uses no
   prompt, tool, model, agent or HTTP API of Claude Code (T5). Focus brings a tab forward and
   that is all it does.
4. **Logins and tokens.** The board's read token lives only in `<state>/board/token.json`
   (mode 0600). It never appears in argv, in the environment of Claude Code, in the pane mod
   or in output. The mod never sees it: `sy` reads it.
5. **Tests use temp homes only.** `HOME`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`,
   `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `SY_HOME`, `CLAUDE_CONFIG_DIR` and
   `PATH` all point into `t.TempDir()`. The `cmd/sy` test binary already isolates them
   (commit `cfbd4fc`); every new package takes its folders from an injected `Env` and never
   calls `os.UserHomeDir` or reads `HOME` itself (a lint test checks this, WP-0). No test
   starts a real opener (`xdg-open`, `open`, `rundll32`), a real Warp or a real
   `claude plugin install` against the network.
6. **Cross-platform.** Linux, macOS and Windows are first-class. Every OS-specific branch
   (paths, opener, console mode, title delivery) is a build-tagged file with a unit test that
   runs on that OS in CI. Warp runs on all three (docs.warp.dev, installation page).

## Key decisions

| # | Decision | Where |
| --- | --- | --- |
| 1 | **One view model, two renderers.** `internal/board` builds a pure, versioned `View` (T2) from either source. `sy board` (Go TUI) and the pane mod (TypeScript) only lay it out. Every word, age, state label and ordering rule is computed once, in Go, so the two cannot drift. The mod gets the `View` as NDJSON from `sy board --follow --ndjson`. | T2, T4, T5 |
| 2 | **Sources: hub first, local always.** With a hub URL, a board token and a reachable hub, the board reads `/v1/overview`, `/v1/sessions`, `/v1/accounts` and `/v1/stream`. Without a hub it folds this machine's outbox with the same code as `sy status`. If the hub goes offline, other machines keep their last hub rows, greyed and marked "hub offline since 14:02". This machine's rows switch to the live local fold. | T3 |
| 3 | **The board token is a desktop-kind device.** `sy board connect` creates `terminal · <machine name>` (kind `desktop`, bound to this machine) through `internal/desktop.Token`. It uses the admin channel when one exists, else a pairing code on stdin. The token is stored in `<state>/board/token.json`. Desktop kind is what the hub already requires before it sends `focus_url`, so **no API, scope or schema change** is needed. The token's `write` scope is never used (the client has no ingest code path; a test checks it). | T3, risk 6 |
| 4 | **The pane is a separate plugin, `switchyard-pane@sy-local`.** It ships in the same local marketplace as `switchyard`. The mod API is early access, so it must not share a manifest with the recording hooks, which must keep working on every Claude Code version. It is opt-in (`sy term setup --pane`). It only spawns `sy` (by absolute path), draws and copies. | T5 |
| 5 | **Titles come from Claude Code's `terminalSequence` hook output,** not from `/dev/tty`. Claude Code hooks run without a controlling terminal, so they cannot open `/dev/tty` (code.claude.com/docs/en/hooks). The documented `terminalSequence` field accepts OSC 0/1/2/9/99/777 and BEL. A new **synchronous** hook command, `sy hook --title <Event>` (timeout 1 s), prints `{"terminalSequence":"\u001b]2;work · api · asked\u0007"}` and nothing else. It writes nothing to the outbox and is silent when titles are off. The recording hook `sy hook <Event>` stays async and silent. | T6 |
| 6 | **Claude Code's own title is turned off only while Switchyard titles are on.** `sy term titles on` sets `/env/CLAUDE_CODE_DISABLE_TERMINAL_TITLE = "1"` in each settings target (a journaled `json_set`, a new pointer in setup.md 5.5) and `terminal.titles = true`. `off` removes both. Setting it in settings `env`, rather than in the launchers, covers plain `claude` too. Wave 0: it also stops the background session-title request and OSC 7501 status reports; `sy term titles on` says so (T6). | T6, T10 |
| 7 | **Tab configs, not launch configurations.** Warp marks launch configurations as legacy. For each account, `sy term warp on` writes `switchyard-<label>.toml` with `name`, `title`, `color` (the nearest of Warp's six chromatic colour names) and one terminal pane that runs the account's launcher. The folder is Warp's per-OS `tab_configs` folder (T8). `sy open <label>` opens `warp://tab_config/switchyard-<label>`. | T8 |
| 8 | **Focus URLs are allow-listed, never trusted.** A `focus_url` comes from a record any machine token can write. `sy term focus` (and the pane, through it) opens it only if it matches `^(warp\|warppreview)://session/[0-9a-f]{32}$`, only on the machine it is for, and only through the OS opener with an argv (no shell). Anything else exits 4 and the opener is never called. | T7 |
| 9 | **`sy ssh` carries the laptop tab to the server.** It runs the real `ssh` with `-o SendEnv=LC_SY_FOCUS -o SendEnv=LC_SY_HOST`, with `LC_SY_FOCUS` = this pane's focus URL and `LC_SY_HOST` = this machine's id. On the server, `sy hook` puts `LC_SY_HOST` into `term.host`. The hub then sends that session's `focus_url` to the laptop's board. | T9 |
| 10 | **Warp's `claude-code-warp` plugin in every folder** is opt-in (`sy term setup --warp-plugin`). It is installed through `claude plugin marketplace add` / `install` as journaled `run` actions per settings target (setup.md 5.2), recorded in the ledger, and removed by `off` / uninstall. `sy` never emits OSC 777 itself, so there is never a second copy of Warp's events. Wave 0: `marketplace add` takes a branch or tag only and the repository has no tags, so the source is `warpdotdev/claude-code-warp#main`; the ledger records the resolved commit and `sy doctor` warns when it moves (risk 7). | T10 |
| 11 | **No new Go dependency, no hub change.** `golang.org/x/term` and `golang.org/x/sys` are already in `go.mod` (wave 0 runs `go mod tidy` only if `x/term` moves from indirect to direct). There is no API, schema or migration change. `record.md` 3.3 only clarifies who sets `host`. | — |

## Open risks

1. **Mod API drift.** The mod API is early access and "moves between releases". The pane is
   a separate plugin with a version floor, `pane-check` runs in CI against the pinned
   version, and `sy board` covers everything without it. When Claude Code updates,
   `sy doctor` warns if the version is above the last checked one.
2. **`terminalSequence` details.** Wave 0 checked in 2.1.296's code that the field is read
   from synchronous hooks only, on every event, and that one JSON object on stdout of
   SessionStart and UserPromptSubmit is parsed as output, not added as context
   (terminal.md, "Claude Code facts"). The title actually changing in a terminal is still
   uncertain until the manual check. Fallback: install
   the title hook on Stop, StopFailure, Notification and PermissionRequest only. Those
   events carry the states that matter.
3. **`CLAUDE_CODE_DISABLE_TERMINAL_TITLE`.** It is only partly verified, and 2026 issues
   report it ignored on Windows and macOS. If Claude Code's title wins, ours is rewritten on
   the next event. Fallback: titles stay opt-in, and doctor reports the fight from a capture
   in the manual check.
4. **Renamed Warp tabs.** Warp tracks `has_custom_title`, but whether OSC 2 then leaves the
   name alone is not verified. Fallback: document it, so the person turns titles off.
5. **`sy ssh` bypasses Warp's SSH wrapper.** Warp's wrapper is a shell function. `sy ssh`
   runs the `ssh` binary, so Warp may not "warpify" that session, and its status icon over
   SSH can be lost. Warp's wrapper forwards only `TERM_PROGRAM`, `WARP_CLIENT_VERSION` and
   `WARP_CLI_AGENT_PROTOCOL_VERSION` (source, `bootstrap/fish.sh`), so focus needs ours. The
   manual check decides. Fallback: `--print-config` for a personal alias, and a note that
   people choose one.
6. **The board token has `write` scope.** It is reused from the desktop kind and never used
   to write (B's test). A read-only machine-bound kind would need a hub change; that is
   a later phase if wanted.
7. **Third-party plugin supply chain.** `claude-code-warp` comes from GitHub and needs `jq`.
   Wave 0 found that `marketplace add` cannot pin a commit (branch or tag only; the
   repository has no tags), so this fallback is the design: the source is `#main`, the
   ledger records the installed commit, `sy doctor` warns on change, and the piece stays
   opt-in.
8. **`LC_*` forwarding.** Debian and Ubuntu sshd accept `LC_*`. Fedora and RHEL list only
   named `LC_` variables in `AcceptEnv`, so `LC_SY_FOCUS` is dropped there. Fallback:
   `sy doctor` on the server reports a session with Warp's `TERM_PROGRAM` but no
   `term.focus_url`, with the one `AcceptEnv LC_SY_*` line for the person to add (never
   written by `sy`).
9. **Unverified Warp details.** These come from Warp's source, not its docs, and may change
   (plan section 14, "Drift"):
   - the focus URL format `warp://session/<32 hex>`;
   - `warp://` handler registration on Linux and Windows (docs: `xdg-open` and
     `Start-Process` only);
   - Windows tab-config paths for Preview;
   - whether a tab config with no `directory` opens in the home folder.

   `sy doctor`'s Warp check and the manual checks catch drift. A failed allow-list match on
   a real `WARP_FOCUS_URL` is reported, never relaxed silently.
10. **Windows console.** VT mode, `rundll32` as the opener, and `.cmd` launchers in tab
    configs are covered by unit tests only, until someone runs the Windows manual check.
11. **tmux.** OSC 2 sets the pane title, and it reaches the outer tab only with
    `set-titles on`. OSC 52 needs `set-clipboard on`. Both are documented, never configured
    by `sy`.
12. **Phase 6 overlap.** `internal/desktop` is called by `sy board connect`. If phase 6's
    wave 2 is still open, any change to `desktop.Token`'s signature goes through its owner.
