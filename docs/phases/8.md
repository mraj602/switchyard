# Phase 8: Phone store app

From plan sections 11, 12 and 16. Branch `phase-8`, tag `v0.8`. Needs phase 4 (pairing,
devices, the alert engine, action tokens, the PWA screens). It reuses phase 5's dial guard
(`internal/hub/push/netguard`) and phase 4's test seams (`fakeclock`, the fake push
services). Phase 8 has three parts:

1. **An Expo app** in a new top-level `phone/` folder. It talks to the same hub API as the
   PWA, with the same screens (Now, Sessions, Session, Accounts, More). It pairs by QR or by
   address plus code, and keeps its token in the OS keychain.
2. **Native pushes from the hub** through a third channel, `expo`, next to Web Push and ntfy.
   Pushes carry **Open**, **Snooze 15 min** and **Seen** buttons that call the existing
   `/v1/actions/{token}`.
3. **Widgets and a Live Activity**: small and medium home-screen widgets on iOS and Android,
   and an iOS Lock Screen countdown to a limit reset.

**Code only, no store.** Agents write and test code on Linux. They never submit to the App
Store or Google Play, never sign, never touch EAS credentials and never run an EAS build.
Developer accounts, push credentials, TestFlight, APK builds and every real-device check are
manual steps for you, listed under "Manual steps".

This file says who builds what, in which files, and how it is proven. In wave 0 the
**Contract** sections (P1 to P13) move to a new `docs/spec/phone.md` (app side) and a new
section 12 of `docs/spec/push.md` (hub side), which then become the source.

Screens: `docs/design/screens/` `PhoneNow`, `PhoneSessions`, `PhoneSession`,
`PhoneAccounts`, `PhoneAlerts`, `PhonePair` (as built for the PWA in phase 4) and
`PhoneLock` (the push with three buttons, the widgets and the countdown).

## Hard rules

1. **No store, no signing, no credentials.** No agent runs `eas build`, `eas submit`,
   `eas credentials`, `eas login`, `eas init`, `fastlane`, `xcodebuild archive` or a Gradle
   release task, and none creates an Apple, Google, Firebase or Expo account or project. No
   credential file is ever written or committed: `*.p8`, `*.p12`, `*.mobileprovision`,
   `*.keystore`, `*.jks`, `google-services.json`, `GoogleService-Info.plist`, a service-account
   JSON or `credentials.json`. `phone/scripts/check-no-secrets.mjs` (wave 0) fails the
   check if one appears in the tree or in `git ls-files`. `eas.json` is committed with build
   profiles only and no secrets.
2. **Continuous native generation.** `phone/ios/` and `phone/android/` are generated by
   `expo prebuild`. They are never committed (`.gitignore`) and never hand-edited. Every
   native change is a config plugin or a library's plugin options in `app.config.ts`.
3. **The token stays in the keychain.** The device token lives only in `expo-secure-store`.
   It never appears in logs, in AsyncStorage, in the widget or Live Activity data (the App
   Group), in a push payload, in a deep link or in an error message. A lint rule and a jest
   test check this (WP-P).
4. **Read, snooze, seen. Nothing else.** As on every Switchyard surface, the app never
   types into a session, approves anything or changes global rules. It is a `phone` device
   (scopes `read`, `push`, tokens.md 3). Owner features (pairing other devices, rules,
   channels, the devices list) stay on the board and the desktop app.
5. **Web Push and ntfy are byte-identical.** Every existing push golden, engine scenario and
   end-to-end test passes unchanged. The `expo` channel is added beside them.
6. **Tests are offline.** No jest test touches the network. No Go test calls `exp.host`:
   they use `expotest`, a fake Expo push service. Only `npm ci` and the optional
   `expo-doctor` step need the network.
7. **Pinned and at least 14 days old.** Every npm dependency is an exact version in
   `package.json`, with `package-lock.json` committed and installed with `npm ci`. Versions are
   the ones Expo SDK 57 bundles (`expo/bundledNativeModules.json` of `expo@57.0.26`), all
   released on or before 2026-09-29 (table in P1). Go gets no new module.

## Key decisions

| # | Decision | Where |
| --- | --- | --- |
| 1 | **Expo SDK 57, not 58.** `expo@58.0.0` exists but sits on the `next` tag and Expo calls SDK 58 a beta. SDK 57 (stable since 2026-06-30) is pinned at `expo@57.0.26` (2026-09-29), with React Native 0.86.3, React 19.2.3 and TypeScript 6.0.3 (the SDK 57 template's choice). Minimums: iOS 16.4, Android 7 (minSdk 24), Node 22.13. | P1 |
| 2 | **Native pushes go through Expo's push service**, not direct APNs/FCM. A store app can only be pushed with the publisher's APNs key and FCM project. A self-hosted hub cannot hold those secrets for every user, and asking each hub owner to create their own would mean their own app build. Expo holds the credentials (uploaded once by you), so the hub needs no Apple or Google secret, only an optional Expo access token. The cost: Expo, Apple and Google can read the push text (Expo says it holds it only in memory and queues while delivering). Private pushes (push.md 5.5) remain the answer, and the Expo channel also drops `remote_url` in private mode. Direct APNs/FCM and a project relay are later options behind the same `Sender` (P8.1). | P8 |
| 3 | **No pairing, scope or route change.** The app claims with `secret` or `code`, `expect_kind: "phone"` and `cookie: false`, and stores the token from the body. The API changes only by **enums and fields**: `expo` in the channel and target kinds, `expo_token`/`platform`/`app` on target registration, the Expo channel settings, `prefs.widgets`, and `expo_refresh_min`. There are no new paths, so the route tables do not change. | P10 |
| 4 | **Schema v6** (`0006_expo.sql`): seed the `expo` channel row, add `push_target.meta` (platform, app version) and `delivery.ticket` / `delivery.receipt_at` for Expo's asynchronous receipts. | P10 |
| 5 | **Receipts are checked asynchronously.** Expo's send answer is a ticket. Whether APNs/FCM accepted it (and `DeviceNotRegistered`) comes from `getReceipts` about 15 minutes later. The sender returns the ticket id in a new `Result.Ref`, the engine stores it in `delivery.ticket`, and a receipts poller in the `expo` package marks targets gone. | P8.4 |
| 6 | **Buttons use the existing action tokens.** The push's `data` is the push.md 6.5 payload unchanged, with `actions.snooze` / `actions.seen`. Notification category `sy_alert` (no `-` or `:`, an Expo rule) has Open, Snooze 15 min and Seen. Snooze and Seen POST `/v1/actions/{token}` with no credential, so they work without the keychain token. | P6 |
| 7 | **iOS widgets and the Live Activity use `expo-widgets`** (official, SDK 57, iOS only), written in JSX with `@expo/ui/swift-ui`, so there is no Swift in the repo. **Android widgets use `react-native-android-widget` 0.22.1**, also JSX. Fallbacks if either fails to build: `@bacons/apple-targets` 5.0.0 with SwiftUI files, and `expo-widgets`' Android support when SDK 58 is stable (risks 1, 2). | P11, P12 |
| 8 | **Widgets show a snapshot, the clock does the rest.** The app writes a `WidgetSnapshot` (counts, rings, reset times, `as_of`) and a precomputed timeline. Countdowns are `Text` with `timerInterval`/`date` (iOS 16+), so they tick without refreshes. The hub sends a silent `refresh` push when the needs-you count or a ring changes, at most once per `expo_refresh_min` (15) per target, so widgets stay fresh without the app open. | P9, P11 |
| 9 | **The Live Activity is started by the app, locally.** "Count down on Lock Screen" on an account card, or automatically when a limit push is opened. It ends at the reset. No push-to-start and no remote updates: both need direct APNs with the `liveactivity` push type, which Expo's push service does not offer. | P12 |
| 10 | **Polling, not SSE, in the app.** React Native's `fetch` cannot stream a response body. While the app is in the foreground it polls `/v1/overview`, `/v1/sessions`, `/v1/accounts` and `/v1/alerts` every 15 s, and at once on a push or on returning to the foreground. | P5 |
| 11 | **expo-router with the PWA's routes.** The push `url` (a hash route such as `/#/sessions/<id>?alert=…`) maps one to one onto app routes through an allow-list. The custom scheme is `switchyard://`. Universal links / App Links are out (each hub is a different domain). | P4, P7 |
| 12 | **Pure logic is separate and tested.** Everything that decides something (pairing input, hub client, routes, tap choice, notification responses, snapshot, timeline, countdown choice, formatting) lives in `phone/src/lib/**` with no React Native import, and is tested in jest. Screens and widgets are thin. | P1 |
| 13 | **Local runs are the gate.** GitHub Actions cannot run at the moment (account billing problem). The `phone.yml` workflow is written and pinned, but `make phone-check` (typecheck, lint, jest, secrets check, Android prebuild check) plus `go test ./...` run locally decide whether a WP is done. This machine has an Android SDK, so `make phone-android-debug` (an unsigned debug compile, never distributed) is an optional extra local gate. iOS compiles only on a Mac, by hand. | Test plan |

## Open risks

1. **`expo-widgets` maturity.** The package began as an alpha in SDK 55 (January 2026). The
   SDK 57 docs carry no alpha or beta label, but none was confirmed either way. Widget
   components cannot use hooks or state, and countdown support rests on `@expo/ui` `Text`
   `timerInterval` / `dateStyle: "timer"` (documented, iOS 16+). Fallback:
   `@bacons/apple-targets` 5.0.0 (2026-07-17) with SwiftUI files in `phone/targets/` and its
   `ExtensionStorage` for the App Group. The snapshot and timeline logic do not change. Wave 0
   fact 3 decides early.
2. **`react-native-android-widget` with SDK 57 / React Native 0.86.** Its peer range is
   `expo >= 54`, but New Architecture and RN 0.86 compatibility were not confirmed, and its
   docs site was only partly readable. Fallback: wait for `expo-widgets`' Android support
   (SDK 58, beta now) and ship Android without widgets in v0.8.
3. **Notification actions while the app is killed.** On Android the background task runs on
   action taps (documented). On iOS, whether a non-foreground action reaches the JS handler
   when the app was killed is unverified. Fallback: `BACKGROUND_ACTIONS_IOS = false` (Snooze
   and Seen open the app briefly), decided by the manual check.
4. **Background refresh is best effort.** iOS throttles `content-available` pushes and may
   drop them in Low Power Mode or for an app the person rarely opens. The hub caps refreshes
   at one per 15 minutes per target. Widgets also show "as of 14:02" after an hour, so stale
   data is visible, not wrong. The background task also needs the tailnet to reach the hub.
5. **Push text leaves the hub.** With Expo, the text of a non-private push is readable by
   Expo, Apple and Google. Expo's FAQ says contents stay only in memory and queues, but no
   formal privacy statement was found. Private mode removes the text and `remote_url`.
   End-to-end encryption is a non-goal.
6. **iOS native compilation is unproven on Linux.** Wave 0 fact 2 passed: `expo prebuild
   --platform ios` works on Linux and generates the widget extension, so the iOS config is
   checked locally. Pods and Swift compilation still happen only on a Mac (manual) or in the
   `ios-sim` job, and errors there surface late. Jest never proves native compilation of
   either platform.
7. **Unverified Live Activity limits.** The 8-hour active and about 12-hour lock-screen
   limits are widely cited but were not confirmed from Apple's documentation. `LIVE_MAX_H` is
   one constant. If iOS ends an activity early, the countdown simply disappears.
8. **No replace-by-tag.** Web Push uses `Topic` and the service worker uses `tag` to replace
   a notification. The Expo API has no collapse field we could verify, so a snoozed re-push
   shows as a second notification. Mitigation: the app dismisses earlier notifications with
   the same `data.tag` when it runs (foreground or background task).
9. **Expo as a dependency.** If Expo's service is down or changes its API, native pushes stop
   while Web Push and ntfy keep working (the person can keep an ntfy target as a backup). If
   abuse forces enhanced security on, the hub needs the access token (manual step 2). The
   base URL setting leaves room for a relay.
10. **API drift against the fake.** `expotest` is built from Expo's docs. A real-service check
    is a manual device step (the test push shows Expo's real answer). Receipt timing (about
    15 minutes) is from the docs.
11. **SDK churn.** SDK 58 will become stable soon after this phase starts, and Xcode 27 builds
    will require the UIKit scene lifecycle (`ios.enableSceneSupport` in
    `expo-build-properties`, SDK 57.0.23+). Phase 8 stays on 57; an upgrade is a separate
    change with `npx expo install --fix` and the same gates.
12. **Credentials expire and break silently.** A revoked APNs key, a deleted FCM service
    account or a wrong bundle id shows up as `InvalidCredentials` tickets. `sy doctor` and
    Settings show the last receipt error, and the README lists the fix.
13. **CI cannot run.** Until billing is fixed, nothing checks Linux-only assumptions on a clean
    runner, and nothing builds iOS at all. Local gates (`make phone-check`, `go test`, the
    optional Android debug compile) are the evidence, and the iOS build is proven only by
    your TestFlight build.
14. **Reachability.** As with the PWA, opening the app, Seen and Snooze need the tailnet;
    pushes do not. If Tailscale's VPN is off, Snooze fails, and the app says so when opened.
